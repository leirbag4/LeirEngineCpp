1. Introducción — dos caminos, un solo motor

LeirEngine tiene dos maneras de construir tus sistemas, y ambas comparten la misma fuente de datos:

Camino OOP (default)
→
Scene · CoreObject · AddComponent
→
Mismo almacenamiento ECS
Camino ECS (power users)
→
World · Record · Field · Query · System
→
Mismo almacenamiento ECS

Esta guía documenta el camino ECS: control directo de entidades, componentes de datos, queries, sistemas con scheduling paralelo, comandos diferidos y almacenamiento en columnas SIMD — sin pasar por el facade orientado a objetos. Úsalo cuando necesites simulación masiva, procesamiento paralelo o acceso fino a la memoria.

2. El vocabulario (nombres propios)

World
El contenedor: records, campos, pools, journal y registro de hybrids.
Entity / Record
Handle generacional de entidad: {índice, generación}. Nunca resuelve handles viejos.
TypedPool<T>
Pool de campos (AoS): filas POD contiguas, sparse-set, add/remove O(1).
SoAPool<T>
Pool de columnas SoA: una columna contigua por campo, lista para SIMD.
OwnedGroup<Ts...>
Query cacheada por journal, con orden estable y ForEach sin chequeos.
CommandBuffer
Cambios estructurales diferidos (create/destroy/add/remove), thread-safe, replay en sync points.
ISystem
Un paso del simulador con acceso declarado a los campos.
SystemPipeline
Fases FixedUpdate → Update → Render, scheduling topológico paralelo.
JobSystem
Thread pool con ParallelFor y Dispatch/WaitAll (en web, inline).
HybridComponent<T>
Faceta OOP boxeada en el ECS: Component clásico con lifecycle dentro de un World.
Tags
Marcadores vacíos (Tag3D/Tag2D/TagUI, Active) para filtrar familias.
HierarchyTree
Scene graph compacto: parent / firstChild / nextSibling / depth por índice.
TransformSystem
Poses mundiales con dirty-frontier, lossy-preserve y SIMD.

3. World y Record — entidades generacionales

Un Record es un handle generacional: cuando destruís una entidad, su índice se recicla pero la generación sube, así cualquier handle viejo queda inválido de forma segura. El índice 0 está reservado como "entidad nula" (estilo EnTT).

World world;

// Crear records.
Entity hero = world.Create();
Entity foe  = world.Create();

// Los records son generacionales: destruir y re-crear NO revalida handles viejos.
world.Destroy(foe);
Entity fresh = world.Create();   // quizá reutiliza el índice, con otra generación
bool alive = world.IsAlive(foe); // false — el handle viejo nunca resuelve

4. Campos — componentes de datos (POD)

Un campo es simplemente un struct POD tuyo. El World lo guarda en un pool sparse-set (one-per-type por entidad, semántica Unity/Godot). Sin macros, sin registros, sin boxes:

// Tus campos son PODs planos — 100% tuyos.
struct Position { float x = 0, y = 0, z = 0; };
struct Velocity { float x = 0, y = 0, z = 0; };

Entity e = world.Create();
world.Add<Position>(e) = { 0, 0, 0 };
world.Add<Velocity>(e) = { 1, 0, 0 };

Position* p = world.Get<Position>(e);  // puntero al POD vivo (AoS)
bool has  = world.Has<Position>(e);
world.Remove<Position>(e);            // O(1), swap-and-pop

El World mantiene un journal de cambios estructurales (add/remove/destroy/create) que alimenta a las queries — nunca tenés que marcar "dirty" a mano:

const std::vector<ChangeRecord>& j = world.GetJournal();
world.ClearJournal(); // el dueño del sync point lo limpia

5. Queries — OwnedGroup (orden estable)

OwnedGroup<Ts...> es el conjunto ordenado de records que poseen TODOS los campos declarados. Se mantiene incrementalmente desde el journal: Sync() consume los cambios y ForEach() itera sin chequeos de membresía por entidad. El orden es estable (remover solo deja un tombstone; el orden de los vivos nunca cambia — clave para z-order y determinismo).

world.Add/Remove/Destroy
→
Journal
→
group.Sync(world)
→
group.ForEach
OwnedGroup<Position, Velocity> movers(&world);
movers.Sync(world);   // consume el journal UNA vez (antes de ClearJournal)
world.ClearJournal();

movers.ForEach([&](Position& p, Velocity& v, Entity e) {
    p.x += v.x * dt;      // lee datos VIVOS del pool
});
Regla: re-sincronizá tus queries después de cambios estructurales (p. ej. tras un CommandBuffer::Replay) antes de leerlas. Una query stale puede referenciar un record destruido.

6. Sistemas — ISystem + SystemPipeline

Un sistema es un paso del simulador. Declarás qué campos lee y cuáles escribe (GetAccess); el SystemPipeline usa eso para el scheduling topológico: dos sistemas que comparten un tipo y alguno lo escribe corren en orden de registro; los independientes corren en paralelo vía el JobSystem.

class MovementSystem : public ISystem {
public:
    MovementSystem(World* w, OwnedGroup<Position, Velocity>* g)
        : ISystem("Movement"), m_G(g),
          m_Pos(w->ComponentType<Position>()),
          m_Vel(w->ComponentType<Velocity>()) {}

    std::vector<SystemAccess> GetAccess() const override {
        return { { m_Pos, true }, { m_Vel, false } }; // escribe Position, lee Velocity
    }
    void Update(float dt) override {
        m_G->ForEach([dt](Position& p, Velocity& v, Entity) {
            p.x += v.x * dt; p.y += v.y * dt; p.z += v.z * dt;
        });
    }
private:
    OwnedGroup<Position, Velocity>* m_G;
    uint32_t m_Pos, m_Vel;
};

SystemPipeline pipeline;
pipeline.Add(&moveSys, SystemPhase::Update);
JobSystem jobs;
pipeline.Run(0.016f, dt, &jobs, &cb, &world); // fases + cb replayed en sync points + paralelo

Las fases son FixedUpdate (timestep fijo, física) → Update (gameplay) → Render (build de comandos). El pipeline aplica el CommandBuffer entre fases, en el hilo del caller, así los cambios estructurales son seguros con sistemas en paralelo.

7. Cambios diferidos — CommandBuffer

Nunca destruyas o agregues componentes mientras iterás: encolá en el CommandBuffer y aplicalo en el sync point. Es thread-safe (mutex), así los sistemas paralelos encolan con seguridad.

CommandBuffer cb;
cb.Destroy(e);                     // destrucción diferida
cb.Add<Health>(e, { 50 });        // add con datos
cb.Remove<Velocity>(e);            // remove

cb.Replay(world);                    // sync point: swap atómico + aplicar fuera del lock

8. Columnas SoA — SoAPool + SIMD

Para sistemas que procesan UN campo en bulk, SoAPool<T> guarda cada campo en una columna contigua de floats — lista para SIMD sin gathers. Complementa (no reemplaza) al TypedPool AoS.

SoAPool<Position> cols;
for (int i = 0; i < 8; ++i) cols.Add((uint32_t)i, { (float)i, 0, 0 });

// Avanzar la columna x de TODOS los records en un solo pase vectorizado (4 a la vez).
std::vector<float> inc(cols.Count(), 0.1f);
Mathf::SimdAddFloats(cols.Col(0), cols.Col(0), inc.data(), cols.Count());

Position p{};
cols.Get(3, p);       // materializar una fila (gather por columnas)
cols.Remove(3);         // swap-and-pop O(1)

9. Facets — HybridComponent

¿Necesitás comportamiento OOP dentro del mundo de datos? Un HybridComponent<T> boxea un Component clásico (con OnStart/OnUpdate/OnDestroy) en el ECS. La instancia la maneja el World; removerla o destruir la entidad la destruye (llamando OnDestroy).

Entity npc = world.Create();
world.AddHybrid<Pinger>(npc);   // boxea un Component OOP

// El driver (Scene o tu loop) tickea el lifecycle OOP cada frame:
for (Component* c : world.GetHybrids())
    c->Tick(dt);   // OnStart una vez + OnUpdate si está activo

Es el puente "híbrido": campos de datos (rápidos, SoA/SIMD) y facets OOP (amigables) conviven en el mismo World — no tenés que elegir entre lo cómodo y lo veloz.

10. Jerarquía y poses — HierarchyTree + TransformSystem

HierarchyTree es un scene graph compacto por índice de entidad (parent, firstChild, nextSibling, depth). TransformSystem computa las poses mundiales con un dirty-frontier (solo subtrees mutados), lossy-preserve exacto al reparentar, y SIMD (MultiplySimd) en el hot path.

HierarchyTree tree;
TransformSystem ts(&world, &tree);

Entity root = world.Create();
ts.SetLocal(root, { { 0, 0, 0 }, Quaternion::Identity(), Vector3::One() });
Entity kid  = world.Create();
ts.SetLocal(kid,  { { 2, 0, 0 }, Quaternion::Identity(), Vector3::One() });
ts.SetParent(kid, root);        // worldPositionStays = true por defecto (lossy-preserve)
ts.Update();

WorldTransform* wt = ts.GetWorld(kid);  // worldMatrix, worldPosition, worldRotation, worldScale

11. Marcadores — Tags

Los tags son componentes vacíos para agrupar familias sin RTTI:

world.Add<Tag3D>(obj3d);   // familia 3D
world.Add<Tag2D>(uiObj);   // familia 2D
world.Add<Active>(e) = { false };  // espejo de CoreObject::SetActive

size_t n = 0;
world.Each<Tag3D>([&](Tag3D&, Entity) { ++n; });

12. Consejos y footguns

  • Nunca iteres y destruyas en el mismo pase. Encolá en un CommandBuffer y reaplicá en el sync point; los iteradores siguen válidos.
  • Re-sincronizá las queries después de cambios estructurales (group.Sync(world) + world.ClearJournal()) antes de leerlas — una query stale puede apuntar a un record destruido.
  • El índice 0 es la entidad nula. No lo uses como nodo real de jerarquía.
  • Las queries son de orden estable: el orden de los vivos no cambia al remover (tombstones). Si necesitás orden por valor, ordená tu propio índice.
  • Logging: en paths per-frame usá XConsole::Trace/Debug, nunca Info/Warning/Error (evitan el feedback loop del ConsolePanel).
  • Debug vs Release: los benchmarks del motor se miden en Debug (~10-30× más lento por diseño). Para números reales, compilá con /O2.
