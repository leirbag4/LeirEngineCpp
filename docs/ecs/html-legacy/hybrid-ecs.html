1. El viaje: de OOP a data-oriented

LeirEngine nació con la arquitectura clásica orientada a objetos: CoreObject con un Transform, un árbol de hijos, y componentes tipo Unity. Funcionaba, pero cada objeto era una caja (unique_ptr) y GetComponent hacía casts lineales. Para escalar a miles de entidades necesitábamos datos contiguos, procesamiento en lotes y paralelismo sin carreras.

El motor fue migrado al ECS en fases (TODO_HYBRID_ECS.md), pero con una regla de oro: la API amigable no cambia. CoreObject::AddChild, SetParent, AddComponent<T>, GetComponent<T> siguen funcionando igual — solo que por debajo ahora delegan al ECS.

CoreObject / Scene (OOP)
→
facade → delega
→
World / Entity / Pools
→
SIMD + Jobs

El resultado es un diseño híbrido (como Unity DOTS, pero con nuestras decisiones): componentes de datos puros (rápidos) y componentes OOP boxeados conviven en el mismo almacenamiento.

2. Arquitectura en capas

API pública OOP — Scene · CoreObject · Transform · AddComponent/GetComponent
API pública ECS (Fase 3) — World · Entity · OwnedGroup · ISystem · SystemPipeline · CommandBuffer
Sistemas de dominio — PhysicsSyncSystem · AudioSyncSystem · TransformSystem · RenderPipeline
Núcleo ECS — World (journal, hybrids) · TypedPool · SoAPool · OwnedGroup · HierarchyTree · SystemPipeline · CommandBuffer
Infraestructura — JobSystem (thread pool) · Mathf (Simd4f/SoA) · XConsole · Settings
Toda la capa OOP es un facade sobre el mismo núcleo ECS — una sola fuente de datos.

Los headers públicos viven en engine/include/LeirEngine/ con LEIR_API; los templates (pools, grupos) son header-only (sin export — dllexport de templates rompe el link en MSVC). Los detalles internos de conversión (p. ej. Jolt ↔ Vector3) NO se exponen.

3. Entidades y generaciones

Una Entity es un handle de 2 campos: { uint32_t index; uint32_t generation; }. El índice 0 está reservado como entidad nula (estilo EnTT). Al destruir una entidad, su índice vuelve a una free-list y su generación sube — cualquier handle viejo deja de resolver.

Destroy(3) → gen pasa de 1 a 2 → el handle viejo {3,1} ya no resuelve (IsAlive false).
struct Entity {
    uint32_t index = kNullIndex; // kNullIndex = 0
    uint32_t generation = 0;
    explicit operator bool() const { return index != kNullIndex && generation != 0; }
};
// World::Destroy: limpia todos los pools del índice, swap-and-pop en m_LiveIndices,
// ++generación, push a la free-list. Reciclaje seguro.

Ventajas: sin punteros colgantes, sin "garbage" de ids, handles baratos (8 bytes). Costo: un salto de indirección por acceso de componente — que los pools resuelven con sparse-set (sección 4).

5. Journal y OwnedGroup (orden estable)

El World registra cada cambio estructural en un journal: { entityIndex, typeId, kind: Created/Destroyed/Added/Removed }. Las queries son conjuntos derivados del journal: Sync() las reconcilia y ForEach() itera sin chequeos por entidad.

world.Add<T>(e)
→
Journal + ChangeVersion++
→
group.Sync(world)
→
ForEach (O(miembros))
OwnedGroup<MeshRenderer, Active, WorldTransform> renderables(&world);
renderables.Sync(world);   // consume el journal
world.ClearJournal();      // el dueño del sync point limpia
renderables.ForEach(fn);     // lee datos VIVOS de los pools

Orden estable (tombstones)

Remover un miembro NO reordena: solo deja un tombstone (row muerta) reutilizable. Así el orden de los vivos nunca cambia — crítico para z-order de render, serialización y simulación determinista.

7. TransformSystem — dirty-frontier + lossy-preserve + SIMD

Dirty frontier

Los LocalTransform (pos/rot/scale en espacio del padre) son authored; los WorldTransform (matriz mundial + pos/rot/scale LOSSY) se computan top-down solo para sub-trees mutados. Cada SetLocal marca el subtree dirty; Update() recorre la frontera y garantiza que el padre se limpia antes que el hijo.

SetLocal(e) →
MarkSubtreeDirty(e)
→
Update(): por cada dirty, EnsureClean(parent) → ComputeWorld
→
WorldTransform fresco

Lossy-preserve exacto (mejor que Unity)

Al reparentar con worldPositionStays=true, el world capturado se preserva re-derivando el local: la escala local se divide por el largo de las columnas de parentWorld · localRot. Esto preserva la escala lossy exacta incluso con padre rotado + escalado no-uniforme — Unity divide por el lossy del padre y aplasta al hijo en ese caso. Guard epsilon (1e-8) para ejes a escala 0 (evita NaN).

// TransformSystem::SetWorldScale / SetParent (worldPositionStays):
const Matrix4x4 combined = parentWT->worldMatrix * localRotM; // localRot ya compensa al padre
const Vector3 colLen = ComputeColumnLengths(combined);   // largos de columnas
lt.scale = { scale.x / (colLen.x > 1e-8f ? colLen.x : 1.0f), ... };
Límite honesto (modelo TRS): si el padre está rotado + escalado no-uniforme, la matriz de mundo del hijo puede conservar shear que el TRS local no puede expresar — es una limitación compartida con Unity (que encima deforma la escala). Documentado, no un bug.

SIMD

El hot path parentWorld × local usa Matrix4x4::MultiplySimd (splat+FMA por columna, 16 FMA + 4 stores) — 5.6× vs escalar en Release. Todo SIMD pasa por Math/Simd.h.

8. La capa SIMD

Toda la matemática vive en Mathf (regla del repo: nunca std::/glm sueltos). Simd4f son 4 floats con load/store/add/mul/fma/splat/lane/min/less/or por plataforma:

PlataformaBackendEstado
x64 Windows/LinuxSSE2 (baseline)✅ (AVX/AVX-512 documentado, futuro)
ARM64 (Apple Silicon/Android)NEON float32x4_t✅
Web (wasm)SIMD128 v128_t✅
Otrosescalar✅ fallback

Consumidores actuales: Matrix4x4::MultiplySimd (poses), Mathf::SimdAddFloats (columna SoA, x3.7 en 4M floats), Frustum::TestSphere/CullBatch (frustum cull: /O2 x3.55 per-call; batch lane=renderable x1.48 incluso en Debug).

9. Sistemas y scheduler paralelo

Cada ISystem declara qué tipos lee/escribe (GetAccess). El SystemPipeline hace scheduling topológico por niveles dentro de cada fase (FixedUpdate → Update → Render): dos sistemas conflictan si comparten un tipo y alguno lo escribe; los de un mismo nivel (independientes) corren en paralelo vía el JobSystem.

nivel 0
MoveSystem (writes Pos)
ExpireSystem (reads Life)
nivel 1
ReadPosSystem (reads Pos)
Move y Expire son independientes (no comparten tipo) → corren en paralelo; ReadPos lee Pos → corre después de Move.
SystemPipeline p;
p.Add(&moveSys,  SystemPhase::Update);  // escribe Position
p.Add(&expireSys, SystemPhase::Update);  // lee Lifetime
JobSystem jobs; // thread pool
p.Run(0.016f, dt, &jobs, &cb, &world);

Sin jobs (o 1 thread) corre secuencial con resultados idénticos (verificado en ECSTest). El JobSystem::ParallelFor usa chunking (cada grab toma 64 índices) — sin chunks el fetch_add por índice hacía el paralelo más lento que el secuencial (0.14×); con chunks 5× más rápido.

10. CommandBuffer y sync points

Los cambios estructurales diferidos (create/destroy/add/remove) se encolan en un CommandBuffer mientras se itera; Replay los aplica en el sync point (entre fases, en el hilo del caller) — nunca a mitad de iteración. Es thread-safe (mutex): los sistemas paralelos encolan con seguridad.

Sistemas paralelos
→
CommandBuffer (mutex)
→
Sync point: Replay (swap atómico + aplicar)
→
World actualizado

Verificado en ECSTest: un sistema en fase Update encola un destroy y el replay del sync point lo aplica (entidad muerta, viva intacta, buffer drenado).

11. Componentes híbridos (data + OOP)

HybridComponent<T> boxea un Component OOP (con OnStart/OnUpdate/OnDestroy) dentro del ECS. Es move-only (el unique_ptr necesita moves correctos para el swap-and-pop del pool). Al remover la entidad o el componente, el box llama OnDestroy() y des-registra la instancia del registro de lifecycle del World.

world.AddHybrid<Pinger>(npc);   // boxea + registra en GetHybrids()
Pinger* p = world.GetHybrid<Pinger>(npc);
for (Component* c : world.GetHybrids()) c->Tick(dt); // driver del lifecycle

Component::Tick llama OnStart una vez y luego OnUpdate si el componente está activo. Este es el puente que permite que CoreObject::AddComponent<T> siga funcionando sobre el ECS.

12. Scene = el driver fusionado

Scene fusiona el mundo OOP con el ECS: cada CoreObject es una entidad backed; su Transform es un facade sobre el TransformSystem; sus componentes de datos viven en pools. El OnUpdate es la orquestación completa:

StepPhysics
→
PhysicsSyncSystem
→
AudioSyncSystem
→
hybrid lifecycle (Tick)
→
obj->OnUpdate
→
transforms.Update()
→
SceneGroups.Sync + ClearJournal
void Scene::OnUpdate(float dt) {
    m_Physics.Update(...);          // StepPhysics
    m_PhysicsSync.Update(m_World, m_Transforms);
    m_AudioSync.Update(m_World);
    for (Component* c : m_World.GetHybrids()) c->Tick(dt);
    for (CoreObject* o : m_Objects) o->OnUpdate(dt);
    m_Transforms.Update();
    m_RenderGroup.Sync(m_World); m_SpriteGroup.Sync(m_World);
    m_CameraGroup.Sync(m_World);  m_LightGroup.Sync(m_World);
    m_World.ClearJournal();
}

El render corre después (OnRender) leyendo los grupos journal-fresh — nunca stale.

13. Render data-oriented (cull SIMD)

El RenderPipeline consume ISceneStorage (los grupos journal-synced) y arma el render list en una pasada: cull de frustum (6 planos, SIMD), copy SIMD de la world matrix, y draw command build en columnas por campo. Los draws fuera del frustum se saltan completos.

Renderables group
→
Frustum::CullBatch (columnas, 4/lote)
→
renderList (columnas)
→
Draw (salta culled)

La esfera de cull es conservadora: radio local de la malla (lazy + cacheado) × max-axis del worldScale — sin falsos negativos (la rotación preserva |v|). Paridad SIMD==escalar verificada por-elemento en 100k esferas (bit-exacta, asociación FMA alineada).

14. Física y audio a data

PhysicsSyncSystem

RigidBody y Collider son componentes de datos (POD en pools). El sistema crea el body Jolt lazy desde el collider + pose mundial y sincroniza por tipo: Dynamic (Jolt→mundo vía TransformSystem::SetWorld*), Kinematic (mundo→Jolt), Static (nada). El dtor del RigidBody destruye el body; SetType destruye y el sistema recrea.

AudioSyncSystem

AudioSource es move-only (el SoundId se transfiere al mover y se libera en el dtor — necesario para el swap-and-pop del pool). OnAwake crea el source (lo llama AddComponent); el lifecycle (play-on-awake + sync 3D) lo maneja el sistema leyendo la pose mundial. El AudioListener es un marcador: el sistema pushea pos+orientación al backend.

Ambos corren en Scene::OnUpdate. Los headers públicos jamás exponen tipos Jolt/SoLoud.

El frame time del editor es igual o menor que antes del ECS (sin regresión, verificado visualmente) — los números altos son estrés sintético de 100k, no costos por-frame reales.

16. Plataformas y CI

  • Desktop (Windows/Linux/macOS): engine completo, JobSystemThreadPool (Jolt multithread), SSE2/NEON.
  • Web (wasm): JobSystem inline (decisión permanente single-thread — sin SharedArrayBuffer/COOP-COEP), Jolt JobSystemSingleThreaded, SIMD128, timestep fijo 1/60 con acumulador. Stack wasm 16 MB (ProcessBodyPair a -O0).
  • CI (GitHub Actions): 3 OS con MSVC/cl, + job Emscripten. Tests: PhysicsTest, SlangExportTest, ECSTest (ctest 3/3).

17. Qué sigue

  • AVX/AVX-512 dispatcher (documentado, futuro): detección __cpuid+XGETBV, variantes por TU (/arch:AVX2/AVX512), punteros a función con fallback SSE2. La máquina del dev (i5-1035G1, Ice Lake) tiene AVX2 + AVX-512.
  • Fase 3 — API pública ECS expuesta y documentada (docs/ecs-public-api.html + demo ECSPublicDemo).
  • Storage SoA por campo en pools concretos — la primitiva (SoAPool) ya existe; se adopta cuando un sistema lo necesite (partículas, crowds).
